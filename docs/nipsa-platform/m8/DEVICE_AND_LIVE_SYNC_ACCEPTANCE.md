## Live website-reference protocol

External refresh is currently **off by default**. Previously blocked production requests were not retried repeatedly under the unchanged environment policy. Do not set a live-success status until this protocol passes. No production publication, DNS, hosting or paid action is authorized by this document.

The runtime downloader deliberately fixes the website origin to `https://nipsaunilesa.com.ng`; an arbitrary staging-feed origin is not currently configurable. Do not change DNS/hosts, disable TLS checks or use test-only request mapping to claim external verification. Real-origin testing needs a separately approved publication of the genuine public feed. Synthetic change/withdrawal fixtures remain controlled tests unless an isolated staging-origin design is explicitly reviewed; do not seed invented articles into production.

1. **Prerequisites:** approve an isolated HTTPS app/API host with private persistent storage, current Node runtime, secure cookies, trusted TLS/proxy and normal authenticated access. Verify the allowed website origin and correct same-origin PWA `/api/v1` routing. Pages static hosting alone is insufficient. Confirm no credentials/private records enter the public feed.
2. **Publication:** build the approved website revision normally. Validate `out/pharmaideia-content.json` schema/digest and actual exported metadata, including candidate directory warnings. In an approved publication, verify the intended HTTPS feed path returns JSON and appropriate caching metadata; record status, version and generatedAt. generatedAt is build time, not an institutional verification date.
3. **Runtime client:** test from the actual backend process, not only curl. Node's native fetch/proxy/CA configuration must be explicitly verified in that host; an injected local test transport does not prove external DNS, TLS, proxy or CDN behavior. Keep TLS verification and fixed-origin/no-redirect restrictions intact.
4. **Enable only after verification:** configure the existing `PHARMAIDEIA_WEBSITE_FEED_REFRESH=1` setting in the approved staging process. Record admin-only refresh diagnostics; never put tokens or sensitive bodies in screenshots/logs. Confirm first valid fetch and a subsequent conditional request/304 using an accepted ETag. A 304 without prior validated ETag must remain unavailable.
5. **Real change:** use a genuine owner-approved website content revision/publication through the real pipeline, or a separately approved isolated staging-origin arrangement. Within the five-minute backend pull interval, plus active view polling, verify search suggestions, draft preview and stored-message preview update without a PWA redeploy. Select/paste only actual canonical destinations; confirm missing/ambiguous titles are not guessed. Synthetic local fixtures prove controlled behavior only; never create a fictional university event to fill production.
6. **Correction/withdrawal:** correct/remove the staging fixture through the same pipeline. Verify existing references update or show unavailable and lose unsafe/stale active highlighting; private/support and authorized notice views resolve current metadata without exposing another recipient's data. Confirm the public destination actually loads on Android; do not infer HTTP availability from a card alone.
7. **Failure boundaries:** invalid JSON/type/digest, oversized streamed body, attempted redirect, timeout/outage, 403 and recovery. Keep last-good data, no query/body forwarding, bounded backoff, and no repeated 403 requests. A blocked process requires corrected access/configuration and intentional restart; record actual recovery.
8. **Restart/staleness decision:** the implementation keeps last-good feed/ETag in memory and restarts from the bundled snapshot. Test after a withdrawal followed by restart during outage. Before launch, approve and implement/verify an appropriate last-good persistence/expiry/staleness policy; do not silently treat an old fallback as fresh live data. No persistence guarantee is currently claimed.
9. **Rollback and operations:** verify a safe publisher/backend rollback, worker supervision, approved refresh monitoring, cache behavior across CDN/proxy and restore/deletion procedures. Keep private messages, reports, session cookies, result data and account diagnostics out of service-worker/public caches.

These gates require owner-approved infrastructure/source/access. No new Editorial portal is created: its unavailable original source and final publishing integration remain separate dependencies. Record failed/blocked/not-run cases explicitly rather than filling a checklist with assumed passes.
